# Building a real project with the system, and what went wrong

Spanish: [RESULTADOS_PRUEBA_REAL.es.md](RESULTADOS_PRUEBA_REAL.es.md)

FastAPI library-management app, built from scratch in
`/path/to/testcode` using only the system installed via
`pip install opencode-shunt`.

Every figure comes from the `session` table in `opencode.db` and from shunt
telemetry. These are not estimates — they are what was billed. Reproducible
with `shunt costs` from that directory.

| | |
|---|---|
| Date | 10 September 2026 |
| Orchestrator | Claude Opus 4.8 (and Gemini 2.5 Pro at the end — see below) |
| Worker | Gemini 2.5 Flash (Vertex AI, ADC) |
| Total spend for the exercise | **$4.37** across 14 sessions |
| Building the app | **$1.51** across 5 tasks |
| Code generated | 642 lines of Python, 4/4 tests green |
| Real defects found | **4**, all silent |

---

## 1. The headline: delegating mechanical edits was off by default

Same instruction, run twice: once with the orchestrator writing by hand and once
delegating to the worker. Two different tasks, two independent measurements.

| Task | By hand | Delegated | Saving |
|---|---:|---:|---:|
| Write 26 docstrings on business logic | $0.3375 | $0.2065 | **39%** |
| Translate those docstrings to English | $0.2989 | $0.1852 | **38%** |

Tests stayed green in all four cases and the worker did not touch a single line
of executable code. The second measurement used the configuration freshly
generated by `shunt config`, with no manual tweaks.

The important detail is *why* it was off: the default allowlist for
`delegate_edit` was `tests/**`, so the tool that saves the most could not touch
source code. That is defect 4 below.

## 2. The same review, four times

The task “give me a full code review” delegated the reading to the worker and
**then read all six files anyway**. I tried to stop it. The first two attempts
made the bill worse.

| Version | Cost | Cache write | Outcome |
|---|---:|---:|---|
| 1. Original | $0.2549 | 12,393 | baseline |
| 2. Block all re-reads | $0.4687 | 22,385 | **84% worse** |
| 3. Block with economic threshold | $0.3109 | 25,132 | still worse |
| 4. Cap summary length | $0.2228 | 11,541 | **13% better** |

Version 2 is the lesson of the whole exercise: **blocking looks free and is
not**. It costs the turn the model spends receiving the refusal and trying
again. Five refusals bought five turns to keep out a few kilobytes, and the
review went up 84%.

It is the same arithmetic the project already uses to decide whether to
delegate, applied somewhere I had not thought to apply it. Blocking now has its
own threshold: below about 11 KB per file, staying quiet is cheaper than
complaining.

And version 4 shows I was chasing the wrong cause. The problem was not that the
model re-read: it was that the summary it received was worthless.

## 3. The five instructions that built the application

| # | Instruction | Cost | Output | What the system did |
|---|---|---:|---:|---|
| 1 | Build the FastAPI app | $0.5546 | 11,120 | 516 lines of business logic, written by Opus. Correct: that does not get delegated |
| 2 | Explain the loan flow | $0.1261 | 2,445 | 14 KB, under threshold. Read bounded instead of delegating. Correct call |
| 3 | Full code review | $0.2549 | 3,672 | Delegated on its own, then read all 6 files anyway |
| 4 | Write and run tests | $0.2338 | 2,820 | `delegate_write` generated the tests. All 4 pass |
| 5 | Docstrings on business code | $0.3375 | 6,928 | Tried to delegate, allowlist blocked it, Opus wrote them |

Total **$1.5069**.

**How much the worker actually cost, corrected.** An earlier version of this
document said 0.8%, and that was wrong for a reason worth writing down: worker
calls are direct HTTP from our tools, so **they do not create an OpenCode session
and do not appear in `opencode.db`**. Counting only what the database sees —
explorer subagent sessions — the worker looked like it cost $0.014. Adding the
tokens our own telemetry records, the real worker cost in this repository is
**$0.0959, 2.2% of spend**.

In the real repository the ratio is the same: $0.2297 of worker on $11.95, **1.9%**.
Still the margin of the system — the more work crosses that boundary, the
cheaper the session — but three times what we said before.

The lesson is not the number, it is where it came from: measuring a system with
another system's accounting leaves out exactly what that other system cannot see.

## 4. The four defects

None of them threw an error. In all four the system kept working and kept
overcharging, which is exactly the class of failure a test suite does not find.

### 4.1 The summary was longer than the code

A broad question over 17.7 KB of source returned **27.5 KB of prose**.
`bulk_read` promised compression and nothing enforced it, so delegation paid for
a worker call and a round trip to put *more* into the expensive context than
reading the files directly would have.

Fixed: the response carries a character budget in the prompt itself and a cap of
25% of source size, with a second cheap compression pass — done by the worker —
if it overruns. The same review dropped to $0.2228 with the summary at 81%
compression.

### 4.2 Update ate the configuration

`shunt.json` was distributed as if it were code, so `shunt update --force`
replaced it with the template. That left `writerProfile` unset, which sent
delegations to a profile nobody chose, which made the orchestrator write
everything itself without saying so.

I caught it because a delegated edit failed with a 404. Without that 404 it
would have gone unnoticed indefinitely: the system did not look broken, just
expensive.

Fixed: configuration is installed once and never touched, not even with
`--force`. There is a test for it.

### 4.3 The wizard offered models that did not exist

`shunt config` picked from the catalogue without checking what Ollama actually
had downloaded, and `shunt doctor` passed because it checked that the server
responded, not that the model was there. Every delegation died with a 404 and
the work fell back to the expensive model.

Fixed: the wizard offers only what is downloaded and `doctor` verifies the
model, not the port.

### 4.4 The default allowlist turned off `delegate_edit`

It limited edits to `tests/**`, so the tool that saves the most could not touch
source code. It mixed two risks that are not the same: `delegate_write` invents
a file nobody reads, while `delegate_edit` returns a diff that *is* reviewed,
after backup, rejection of disproportionate changes, and a parser pass on the
result.

Fixed: they have separate defaults, with a veto list underneath — CI,
migrations, lockfiles, `.opencode/` itself — that no configuration can override.

## 5. Switching orchestrator to Gemini Pro

After the exercise I repeated the translation task with Gemini 2.5 Pro
orchestrating instead of Opus, same worker, nothing changed except
`shunt config`.

| Orchestrator | Cost | Time | Result |
|---|---:|---:|---|
| Claude Opus 4.8 | $0.1852 | 61 s | 2 files delegated, tests green |
| Gemini 2.5 Pro | **$0.0144** | **16 s** | identical |

**92% cheaper and four times faster, same result.** One task, and mechanical:
Opus is still better at what needs judgement, which is exactly the role that
does not get delegated. But for well-orchestrated mechanical work the difference
is not subtle, and it explains why this project's tests now run on Gemini Pro.

That switch surfaced two more things:

**The delegation floor moves with the boss, and it should.** The catalogue had
one price per provider, and for Google those were Flash prices. With Pro
orchestrating, the threshold would have been computed with prices four times
lower than reality. There are per-model prices now, and the result is that the
same repository delegates from 12.6 KB with Opus and from **23.4 KB with
Gemini Pro**: delegating exists to protect an expensive context, and with a
cheap boss there is less to protect. It depends on the ratio between what the
provider charges to put a token in cache and to re-send it — Anthropic discounts
a cached token 90%, Google 75% — and it recalculates on its own.

**One vendor can hold two roles.** Gemini Pro orchestrating with Gemini Flash
reading is a normal setup, and it is the case the original design got wrong:
read exemptions were keyed by provider, so exempting Google would have exempted
the boss too and switched the whole system off in silence. They are keyed by
model now, and `doctor` fails loudly if the orchestrator ends up on that list.

## 6. Opus vs Gemini 3.1 Pro vs Astra, on a judgement task

Everything above is mechanical work, where delegating always wins. What
actually decides whether you need an expensive orchestrator is: **on a judgement
task, does the expensive model find things the cheap one does not?**

### Setup

A copy of the real repository with **three hand-injected defects** in
`services/runs.py`, a multi-tenant service. The kind that passes a distracted
human review:

| | Defect | Why it is hard |
|---|---|---|
| **D1** | `signal_run` uses `client.get_workflow_handle` directly, skipping `_authorized_handle` and the tenant check with it | Visible by comparing with the other five functions in the file, not by reading this one |
| **D2** | `input_overrides` is applied **after** `validate_inputs`, so overrides are not validated | Both lines are correct; the order is wrong |
| **D3** | In `_authorized_handle` the tenant check ended up inside the `try`, so a non-NOT_FOUND `RPCError` is swallowed and an unverified handle is returned | Requires reasoning about an error path that almost never runs |

Same prompt for all three, no hints: *"find real bugs… for each bug give the exact location, mechanism and consequence. If you find nothing, say so."* Same worker (Gemini Flash), same shunt, one pass each.

### Results

| | Opus 4.8 | Gemini 3.1 Pro | GPT-6 Astra |
|---|---|---|---|
| **Defects found** | **3 of 3** | **2 of 3** | **3 of 3** |
| Which it missed | — | D3 (the error path) | — |
| False positives | 0 | 0 | 0 |
| Bonus | 2 pre-existing real defects | — | cross-file reasoning |
| Cost | $0.3883 | **$0.1692** | $0.6112 |
| Time | 95 s | 88 s | 85 s |
| Price | $5 / $25 per million | $2 / $12 | **$10 / $50** |

**Gemini 3.1 Pro found D1 and D2 and missed D3**, the only one that requires
reasoning about an error path that almost never runs. It did not claim the rest
was clean, which is the important difference: it reported what it found without
signing off on what it had not looked at.

### Note on an earlier version of this table

The first run used **Gemini 2.5 Pro**, which was stale: 3.1 Pro already
existed. With 2.5 the result was **1 of 3**, and it closed with *"the rest of
the service is well designed from a multi-tenant security perspective"* — a false
negative stated with confidence.

Worth writing down for two reasons. One, the gap between generations is not
cosmetic: 1 of 3 with a false "all clean" vs 2 of 3 without it. Two, the
starting error was mine and structural: this project's catalogue had models
written by hand and was two generations behind on **all** providers. That was
fixed by reading OpenCode's model table instead of competing with it, and along
the way it turned out the cache price I had for Gemini Pro was wrong by a factor
of 2.5, which moved its delegation floor from 11.7 KB to 23.4 KB.

**Astra found all three and went further than Opus on one point.** It did not
stop at the file it was given: for D1 it looked up what signals actually exist
and found that `ApprovalGateWorkflow` accepts `approve` and `reject`
(`worker/workflows.py:154-160`), turning "foreign signals can be sent" into
"another client's workflow can be approved". For D2 it gave a concrete input
that breaks (`{"delay_seconds": "not-an-int"}`) and where it blows up
(`worker/workflows.py:45`). **I verified all three citations by hand: exact.**

### What follows, and what does not

This is **one task and one pass each**: not a capacity measurement. With current
models the spread is narrower than it looked: 3 / 2 / 3 out of 3, not 3 / 1 / 3.

The project's thesis still holds, and is better stated. Mechanical work is done
equally well by a model 50 times cheaper, with 78–88% measured savings. Judgement
work separates, but it separates **on the hard defect**: all three saw the
missing authorisation, the cheapest did not see the error path. **The system
exists so you can pay for the expensive model where it matters without paying
for it where you do not**, and the margin is exactly there.

On cost: Astra cost **57% more than Opus for the same score**, being the most
expensive model in the catalogue. Gemini 3.1 Pro got 2 of 3 for **$0.1692, 56%
less than Opus**. If what you do is mostly mechanical review with occasional
judgement, 3.1 Pro is defensible; if security review is the job, the third
defect is exactly the one you want someone to find.

### The failure this test surfaced, which was not the models

The Gemini arm logged **zero telemetry events**. Per our own README that is
indistinguishable from a broken install, so I chased it.

The cause: **OpenCode passed `worktree: "/"` to the plugin.** With that,
`path.resolve("/", "src/app.py")` gives `/src/app.py`, which does not exist.
The `stat` failed and the hook did `return` without saying anything.

The damage went well beyond lost reads: `loadExempt` and `loadConfig` read from
the same root, so **the exemption list came back empty and the economic
arithmetic fell back to defaults that belong to no repository**. The shunt was
loaded, passed every `doctor` check, and did nothing.

What kept it hidden is an asymmetry between models nobody would have guessed.
Over 193 logged reads:

| | Reads | Path the model passes |
|---|---|---|
| Claude Opus | 171 | **absolute** — resolves correctly from any root |
| GPT-6 Astra | 11 | **absolute** |
| Gemini (Pro and Flash) | 9 | **relative** — depends on the worktree being correct |

So: **the same install works or not depending on who orchestrates.** Every
figure in this document is from Opus sessions with absolute paths, so they are
not affected.

Three fixes, in `3.3.0`:

1. `lib/worktree.ts` validates the root instead of trusting it: only accepts one
   that contains the `.opencode` we are installed in, otherwise falls back to
   cwd. Seven tests, because the failure gave no symptom.
2. The two silent `return`s on the read path now log `measure-failed` and
   `not-a-file` with the resolved path. That made it diagnosable in a single
   $0.01 pass.
3. The unknown-session fail-open logs `session-unknown`, and `doctor` warns if
   it exceeds 20% of reads.

The lesson is uncomfortable and worth writing down: I have spent the whole
project saying the danger is silent failures, and the worst one was inside the
guard itself. A test looking for something else found it.

## 7. What remains open

**Additive delegation is still there in small-file repos.** The orchestrator
summarises and then reads anyway, and below 11 KB per file nothing stops it,
because stopping it would cost more than it saves. With the summary now capped
the damage is smaller, but not zero. The likely fix is not more blocking but
summaries with precise enough line ranges that re-reading stops being tempting.

**The savings are mostly on input.** Output is a third of the bill and
`delegate_write` and `delegate_edit` only reach the mechanical part of it. The
orchestrator's reasoning stays intact, and should: that is what you are paying
for.

**One task is one data point.** The two A/B edit measurements are consistent
with each other (38% and 39%), which gives some confidence. The orchestrator
comparison is a single run and should be treated as such.
